# Global CLAUDE.md — Step-Based Development Defaults

> Cross-project defaults for Claude Code. Place at `~/.claude/CLAUDE.md`.
> Companion: `~/.claude/settings.json` (tool permissions). A project's
> `.claude/CLAUDE.md` overrides this file where they conflict.
>
> Kept short on purpose. The rules that must hold every time are enforced by
> hooks and permissions, not by this text. Role-specific detail lives in the
> project's `.claude/AGENTS.md` and skills, and loads only when needed.

---

## When These Rules Apply

Environment, Python, git, code standards and communication sections apply in
every project. The **Step-Based Process** section applies only when the project
has both `plans/CURRENT_PLAN` and `.claude/AGENTS.md`. If it has only one, tell
the user the setup is incomplete and ask how to proceed.

## Default Environment

| Setting          | Default                      | Notes                                      |
|------------------|------------------------------|--------------------------------------------|
| Development OS   | WSL2 (Ubuntu)                | Linux commands only; no Windows paths      |
| Target OS        | Windows                      | Final deployment target                    |
| Language         | Python 3.11+                 | Adjust per project                         |
| Project root     | `~/Projects/<project-name>/` | One folder per project                     |
| Environment      | `.venv/` managed by `uv`     | Created by `uv sync`                       |
| Package manager  | `uv` exclusively             | Never `pip install` or `python -m venv`    |
| Dependency file  | `pyproject.toml`             | Runtime deps in `[project]`; dev tools in `[dependency-groups]` |
| Lockfile         | `uv.lock`                    | Generated by uv; never hand-edit; commit it |

Validate these during discovery and record changes in the project's
`.claude/CLAUDE.md`.

**uv commands:** `uv sync` (build or update the environment), `uv add <pkg>`,
`uv add --dev <tool>`, `uv remove <pkg>`, `uv run <command>` (for example
`uv run pytest`). Never install into a shared or global environment.

## Git Policy — CRITICAL

- **Never** run a git command that writes: `add`, `commit`, `push`, `pull`,
  `tag`, `checkout`, `switch`, `merge`, `rebase`, `reset`, `restore`, `stash`,
  `rm`, `mv`, `clean`, branch creation or deletion.
- Read-only git is fine: `status`, `log`, `diff`, `show`, `branch --list`.
- When a commit is warranted, suggest it with a proposed message. The user runs it.
- Enforced twice: by deny rules in `~/.claude/settings.json` and by the
  project's `guard_bash.py` hook, which also catches chained commands.

## Step-Based Process

**Why:** each step fits one fresh context window, and each step leaves a
complete, timestamped record in `plans/`.

**The loop** (every step after step-000):

1. **Plan** (plan mode, read-only) — draft the next step with the user.
2. **Approve** — the user approves the plan; approval exits plan mode.
3. **Record** — first action after approval: write `plans/step-NNN-<title>.md`
   from `plans/PLAN_TEMPLATE.md`, with the approved plan pasted into its
   final `## Approved Plan` section. Set status `planned`; update `plans/CURRENT_PLAN`.
4. **Stop.** Planning and building never share a context window. After the
   record is written, tell the user to run `/clear` then `/next-step`. Do not
   start implementing in the same session, even if asked to "go ahead"; say
   why and point to `/next-step`. Enforced: the hooks refuse code edits and
   shell writes in a session that started with the previous step completed or
   that recorded a new step plan.
5. **Implement** (fresh session) — carry out the plan; keep Session State current.
6. **Review** — run the `reviewer` subagent; record its report in the plan.
7. **Clear** — complete the Pre-Clear Checklist, suggest `/clear`; the user runs `/next-step`.

Step-000 is produced by `/start` (onboarding and discovery).

**One record.** The step plan file is the only record of a step. Claude Code's
own plan-mode file is not referenced; the approved plan text is copied into the
step plan at step 3 and is append-only from then on (enforced by `guard_edits.py`).

**Statuses:** `planned` → `in-progress` → `implemented` → `completed`;
`rolled-back` marks a superseded plan. Plans are never deleted or overwritten;
a `completed` plan is frozen (enforced).

**Revisions:** if a plan needs a meaningful change mid-step, return to plan
mode, get approval again, then append `### Plan Revision — <timestamp>` to the
Approved Plan section and refresh `Last updated`. Revisions are rare; typos
do not need one.

**Timestamps:** `YYYY-MM-DD HH:MM:SS`, local time, from the system clock. The
harness injects the current time at the start of every turn and on session
start; use that value. If a turn has run more than 10 minutes, run
`date '+%Y-%m-%d %H:%M:%S'`. Never guess. Create-once fields (`Created`,
decision rows, revision headings) are never refreshed; `Last updated` is
refreshed on every meaningful change. The `check_plan.py` hook flags
placeholders, malformed and stale timestamps after each plan edit.

**Every plan records:** user decisions, Claude's decisions with confidence,
blockers and unknowns, priorities (P0/P1/P2), the code plan, session state for
handoff, and the approved plan text. If a decision cannot be attributed to the
user or to Claude's reasoning, record it as an unknown.

## Code Standards

These are Python defaults. A project whose Language row in `.claude/CLAUDE.md`
is not Python follows the standards, test command and lint command recorded
there instead.

- PEP 8; line length 88 (ruff default). `uv run ruff format` and `uv run ruff check`.
- Docstrings: PEP 257, NumPy/SciPy style. Type hints on all public functions.
- `logging`, never `print()`, in application code.
- Explicit over clever. Tests for any non-trivial logic.
- Match `samples/` if present. Treat `baseline/` as read-only (enforced).
- `pyproject.toml` ruff config: `line-length = 88`, `select = ["E","W","F","D"]`,
  `convention = "numpy"`, unless the project overrides it.

## Communication

- Lead with the point. Be direct. Stop at the last relevant fact.
- Present options with your recommendation first and the reason.
- Plain English. Explain each technical term the first time.
- Flag risks and trade-offs; do not bury them.
- Never guess. If uncertain, say so, give your confidence, and ask.

**Questions:** ask anything with distinct answers through **AskUserQuestion**
(1–4 questions per form, 2–4 options each, recommended option first and
labelled "(Recommended)", `multiSelect` when several can apply). Open-ended
questions (describe your goal, where is the code) go in plain text. Never use
it to ask for plan approval; plan mode has its own approval step. Record every
answer that affects the project in the step plan's User Inputs & Decisions.
When a question asks the user to confirm or choose between proposals, write
each proposal in full in the message before the form. An option label is not
the proposal; the user cannot judge what they cannot see.

**Shell commands:** the user is not familiar with the command line. Before any
command, say in one or two sentences what it does, what each flag means, and
whether it reads or changes files; say "this deletes" first if it does. A
repeated read-only command (for example `git status`) is explained in full
once per session, then named briefly. Anything that changes, moves or deletes
files is explained in full every time.
